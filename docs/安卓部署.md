# 安卓平板部署（实测记录）

在红魔平板3 Pro（骁龙 8 Elite / 12GB RAM / Android 16）上跑的完整过程。
**结论：工作台 + 8B 模型能独立跑，但纯 CPU 只有 2.2 tok/s，日常建议连电脑。**

---

## 一、两种用法

| 方案 | 平板做什么 | 速度 | 适用 |
|---|---|---|---|
| **A. 连电脑** | 只开浏览器 | 20~40 tok/s | 日常首选 |
| **B. 平板本地跑** | Termux 里跑工作台 + Ollama | **2.2 tok/s** | 没网、想离线 |

先做 A，随时可以加 B。

---

## 二、方案 A：平板只当浏览器

### 电脑这边

把工作台监听从 `127.0.0.1` 改成 `0.0.0.0`：

```bash
sed -i 's|start.js 5178 127.0.0.1|start.js 5178 0.0.0.0|' \
  ~/.config/systemd/user/xingye-chat.service
systemctl --user daemon-reload
systemctl --user restart xingye-chat
```

### 平板这边

浏览器打开电脑的局域网地址：

```
http://<电脑IP>:5178
```

在外网用 Tailscale：

```
http://100.x.x.x:5178
```

## 三、方案 B：平板本地跑

### 1. 打包（电脑上）

```bash
bash tools/pack-android.sh              # 代码 + 数据（约 1.5MB）
cp <你的GGUF> ~/android-deploy/qwen3-8b-v7k-q4.gguf
```

产物在 `~/android-deploy/`：

| 文件 | 大小 |
|---|---|
| `xingye-chat-android.tar.gz` | 1.5 MB |
| `INSTALL.md` | 部署说明 |
| `qwen3-8b-v7k-q4.gguf` | 4.7 GB |

打包时会**自动改配置**适配平板：

- `proxy` 清空（电脑的代理在平板上不存在）
- `contextWindow` 16384 → **8192**（内存不够）
- `knowledgeSemantic` 关闭（平板没装 embedding 模型）

### 2. 传到平板

**方式一：adb（推荐，40MB/s）**

```bash
adb push xingye-chat-android.tar.gz /data/local/tmp/pkg.tar.gz
adb shell "run-as com.termux cp /data/local/tmp/pkg.tar.gz ~/pkg.tar.gz"
```

> ⚠️ **不能直接推到 `/sdcard`**：Android 11+ 的存储沙箱让 Termux
> 读不到 `/sdcard/Download`（除非用户手动 `termux-setup-storage` 授权）。
> 走 `/data/local/tmp` 中转最稳。

模型同理（4.7GB 约 2 分钟）。

### 3. 装 Termux 环境

Termux 里：

```bash
termux-setup-storage          # 可选，授权后能读 /sdcard
pkg update -y
pkg install -y nodejs
```

### 4. 解压

```bash
cd ~
mkdir -p xingye-chat && cd xingye-chat
tar xzf ~/pkg.tar.gz --strip-components=1
```

### 5. ⚠️ 修 Node.js（最容易踩的坑）

**症状**：

```
CANNOT LINK EXECUTABLE ".../usr/bin/node": cannot locate symbol
"_ZNSt6__ndk113__hash_memoryEPKvm" referenced by ".../usr/bin/node"
```

**原因**：`libc++` 是 29 版，但 node v26 是用 30 版编译的。Termux 的滚动更新
有时会漏掉这个库的依赖关系。

**修复**：

```bash
apt-get install -y --reinstall libc++
node --version     # 应该立刻正常
```

实测从 29 升到 30 后 node 直接恢复，不用重装 node。

### 6. 装 Ollama

Termux 官方源里就有（和你电脑上同一个版本）：

```bash
pkg install -y ollama
```

> ⚠️ **国内直连 Termux 镜像极慢**（实测 10 分钟没下完一个包）。
> 开代理后再装，几秒就完事。

### 7. 建模型

```bash
mkdir -p ~/models
# 把 gguf 放到 ~/models/
cat > ~/models/Modelfile <<'EOF'
FROM /data/data/com.termux/files/home/models/qwen3-8b-v7k-q4.gguf
PARAMETER num_ctx 8192
PARAMETER temperature 0.85
PARAMETER stop <|im_end|>
PARAMETER stop <|endoftext|>
EOF

export OLLAMA_MODELS=$HOME/models/ollama
export OLLAMA_HOST=127.0.0.1:11434
ollama serve &
sleep 8
ollama create qwen3-8b-v7k -f ~/models/Modelfile
```

⚠️ **`num_ctx` 必须是 8192，不要 16384**：

| 项 | 占用 |
|---|---|
| 系统（Android） | 2.5 GB |
| Termux + Node | 1.0 GB |
| 模型权重（Q4_K_M） | 6.5 GB |
| KV cache @8192 | 1.1 GB |
| KV cache @16384 | 2.25 GB ← 容易 OOM |

实测 12GB 机器：模型加载后占 **6.5GB**，系统剩 3.6GB 可用。

### 8. 启动

写个一键脚本 `~/start-tablet.sh`：

```bash
#!/data/data/com.termux/files/usr/bin/bash
export PREFIX=/data/data/com.termux/files/usr
export PATH=$PREFIX/bin:$PATH
export HOME=/data/data/com.termux/files/home
export OLLAMA_MODELS=$HOME/models/ollama
export OLLAMA_HOST=127.0.0.1:11434

command -v termux-wake-lock >/dev/null 2>&1 && termux-wake-lock

pkill -f "ollama serve" 2>/dev/null; sleep 1
nohup ollama serve > $HOME/ollama.log 2>&1 &
sleep 8

pkill -f "start.js 5178" 2>/dev/null; sleep 1
cd $HOME/xingye-chat
nohup node start.js 5178 127.0.0.1 > $HOME/workbench.log 2>&1 &
sleep 5

echo "✅ http://127.0.0.1:5178"
termux-open-url "http://127.0.0.1:5178"
```

```bash
chmod +x ~/start-tablet.sh
~/start-tablet.sh
```

### 9. 开机自启

放进 `~/.termux/boot/`（需要装 **Termux:Boot**，且必须与 Termux 同签名来源）：

```bash
mkdir -p ~/.termux/boot
echo '#!/data/data/com.termux/files/usr/bin/bash
exec ~/start-tablet.sh' > ~/.termux/boot/start-xingye.sh
chmod +x ~/.termux/boot/start-xingye.sh
```

⚠️ 如果 Termux 是手动装的 APK（不是从同一个 F-Droid 源装的 Termux:Boot），
会因为签名不匹配装不上 `com.termux.boot`。此时自启脚本放在目录里也不会执行，
开机后手动敲 `~/start-tablet.sh` 即可。

## 四、实测数据

红魔平板3 Pro（骁龙 8 Elite / 12GB / Android 16）：

| 指标 | 数值 |
|---|---|
| 模型加载 | 6.5 GB（Q4_K_M，8192 上下文） |
| **推理速度** | **2.2 tok/s** |
| 一条 100 字回复 | **约 45 秒** |
| 纯 CPU | 是（Ollama 在 Termux 里没有 GPU 后端） |
| 冷启动加载 | 20~40 秒 |

**体感**：能玩，但要等。连续对话会发热降频，建议别超过 20 分钟。

## 四之二、平板上随时切换「用哪边跑模型」

平板有两种跑法，切换只要一条命令。

### 电脑这边：让 Ollama 监听所有网卡

默认只监听 `127.0.0.1`，平板连不上。加一个 drop-in：

```bash
cat > ~/.config/systemd/user/ollama.service.d/25-lan.conf <<'EOF'
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
EOF
systemctl --user daemon-reload && systemctl --user restart ollama
```

验证（应该三个都 200）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:11434/api/tags
curl -s -o /dev/null -w '%{http_code}\n' http://192.168.1.40:11434/api/tags
curl -s -o /dev/null -w '%{http_code}\n' http://100.124.214.66:11434/api/tags
```

### 平板这边：切换脚本

`~/switch-tablet.sh`：

```bash
bash ~/switch-tablet.sh local     # 平板自己跑（离线，2 tok/s）
bash ~/switch-tablet.sh pc        # 连电脑跑（快约 7 倍）
bash ~/switch-tablet.sh pc 192.168.1.40   # 指定局域网地址
```

切到 `pc` 后工作台配置变成：

| 项 | 值 |
|---|---|
| Base URL | `http://100.124.214.66:11434/v1` |
| 模型 | `qwen3-8b-v7k:latest` |
| 上下文 | 16384（电脑内存充足） |

切到 `local` 后：

| 项 | 值 |
|---|---|
| Base URL | `http://127.0.0.1:11434/v1` |
| 上下文 | 8192（平板内存有限） |

### 实测对比

同一句「多少钱？」、同一个角色（阿梅）：

| 后端 | 耗时 | 速度 |
|---|---|---|
| **电脑**（骁龙…不对，是 RTX 5060 Ti） | **6 秒** | ~20 tok/s |
| **平板**（骁龙 8 Elite 纯 CPU） | **45 秒** | 2.2 tok/s |

**差 7 倍。** 有网就切电脑，没网才用本地。

## 五、其他踩坑

### 安卓版 ClashMeta

```bash
# 下载（注意 release 版本号和 asset 名要对上）
curl -L -o cmfa.apk \
  https://github.com/MetaCubeX/ClashMetaForAndroid/releases/download/v2.11.36/cmfa-2.11.36-meta-arm64-v8a-release.apk
adb install -r cmfa.apk
```

**导入配置的坑**：
- 机场订阅 API 可能返回 **522/525**（Cloudflare 源站问题），跟平板无关
- 用浏览器 UA 会被 403 `The User-Agent has been blocked`
- **可靠办法**：在电脑上起个 HTTP 服务，把 config.yaml 传给平板
  ```bash
  # 电脑
  cd /path/to/config && python3 -m http.server 8099 --bind 0.0.0.0
  # ClashMeta → 配置 → + → 从 URL 导入 → http://<电脑IP>:8099/config.yaml
  ```

**网络设置项要点**（Clash 运行时全部锁死，需先停止才能改）：
- 自动路由系统流量 ✅
- DNS 劫持 ✅
- 系统代理 ✅
- **Stack Mode**：`Mips Stack` 在部分设备上不通，换 `Gvisor Stack`

### Tailscale（实测已打通）

```bash
curl -L -o ts.apk https://github.com/tailscale/tailscale-android/releases/download/1.104.5-t788384763-gd8673104f/tailscale-android-universal-1.104.5.apk
adb install -r ts.apk
```

登录页 `login.tailscale.com` 在国内打不开，**必须先有梯子**才能登录。

**登录后要等 NAT 穿透完成**（几秒到一分钟）。刚加上时 `tailscale status` 会显示
设备在线但 `Active: False` / `CurAddr` 为空，这时候 ping 是 100% 丢包，别以为坏了。
穿透完成后变成：

```
100.77.47.45  np05j  android  active; direct 192.168.1.35:55567
```

⚠️ **平板上的工作台必须监听 `0.0.0.0`**，否则通过 Tailscale IP 访问会 502：

```bash
node start.js 5178 0.0.0.0     # 不是 127.0.0.1
```

### 双向互通后的用法

| 从哪 | 访问什么 | 地址 | 速度 |
|---|---|---|---|
| 平板 | 电脑上的工作台（快） | `http://100.124.214.66:5178` | 20~40 tok/s |
| 电脑 | 平板上的工作台 | `http://100.77.47.45:5178` | 2 tok/s |
| 任何地方 | 两边都可达 | 同上 | — |

实测同局域网走 Tailscale 直连延迟 **6ms**，几乎等于本地。

## 五之二、聊天记录同步（Syncthing，实测跑通）

电脑和平板各跑一份工作台时，两边写的会话要能互通。用 **Syncthing** 双向同步
`~/xingye-sync`（电脑）↔ `~/xingye-chat/data`（平板）。

### 为什么不用 Git / rsync

- Git：这台机器到 GitHub 的 SSH 极不稳定（实测成功率 2/6），不适合做实时同步
- rsync：单向，得自己写冲突解决
- Syncthing：双向、有版本冲突处理、能删能改、走局域网直连不经过公网

### 配对步骤

**1. 拿到两边设备 ID**

```bash
# 电脑
grep -o 'device id="[^"]*"' ~/.local/state/syncthing/config.xml | head -1

# 平板（Termux 里）
grep -o 'device id="[^"]*"' ~/.local/state/syncthing/config.xml | head -1
```

**2. 两边互相加设备**

电脑端 API（key 在 `~/.local/state/syncthing/config.xml` 的 `<apikey>`）：

```bash
KEY=$(grep -oP '(?<=<apikey>)[^<]+' ~/.local/state/syncthing/config.xml)
curl -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"deviceID":"<平板ID>","name":"xingye-tablet","addresses":["dynamic"]}' \
  http://127.0.0.1:8384/rest/config/devices
```

平板同理（用平板自己的 API key）。

**3. 电脑端建文件夹**

```bash
curl -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"id":"xingye-chat-data","label":"星野工作台数据",
       "path":"/home/don0ox1/xingye-sync","type":"sendreceive",
       "devices":[{"deviceID":"<电脑ID>"},{"deviceID":"<平板ID>"}],
       "fsWatcherEnabled":true,"fsWatcherDelayS":3}' \
  http://127.0.0.1:8384/rest/config/folders
```

**4. 平板端接受共享**

平板会收到 pending 邀请：

```bash
curl -H "X-API-Key: <平板KEY>" http://127.0.0.1:8384/rest/cluster/pending/folders
```

在平板建一个同名文件夹指到工作台数据目录：

```bash
curl -X POST -H "X-API-Key: <平板KEY>" -H "Content-Type: application/json" \
  -d '{"id":"xingye-chat-data","label":"星野工作台数据",
       "path":"/data/data/com.termux/files/home/xingye-chat/data","type":"sendreceive",
       "devices":[{"deviceID":"<电脑ID>"},{"deviceID":"<平板ID>"}],
       "fsWatcherEnabled":true}' \
  http://127.0.0.1:8384/rest/config/folders
```

### 忽略规则（电脑端 `~/xingye-sync/.stignore`）

### 实测效果

| 操作 | 结果 |
|---|---|
| 电脑新建会话 | **10 秒内**出现在平板 |
| 内容完整性 | MD5 完全一致 |
| 电脑删除会话 | 平板同步删除 |
| 平板重启后 | 同步继续正常工作 |

### 平板 Syncthing 必须随工作台一起启动

`~/start-tablet.sh` 已经包含了：

```bash
mkdir -p $HOME/logs
if ! pgrep -f "syncthing serve" >/dev/null; then
  nohup syncthing serve --no-browser --gui-address=127.0.0.1:8384 > $HOME/logs/syncthing.log 2>&1 &
  sleep 6
fi
```

⚠️ **坑**：Termux 里的 syncthing 进程有时会「在跑但没监听端口」（启动失败留下的僵尸进程）。
判断方法：

```bash
curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8384/rest/system/status
# 000 = 没监听，需要 pkill -f syncthing 后重启
```

## 六、adb 速查

```bash
# 设备
adb devices -l
adb shell getprop ro.product.model
adb shell "cat /proc/meminfo | head -3"
adb shell "df -h /sdcard | tail -1"

# 找占空间的 App
adb shell "du -sk /sdcard/Android/data/* 2>/dev/null | sort -rn | head -10"

# Termux 里执行命令（不用打开 App）
adb shell "run-as com.termux sh -c 'export PATH=/data/data/com.termux/files/usr/bin:\$PATH; <命令>'"

# 截图
adb shell screencap -p /sdcard/s.png && adb pull /sdcard/s.png

# 点按（坐标是屏幕像素）
adb shell input tap X Y
adb shell input text "文本"
adb shell input keyevent 4    # 返回
```
